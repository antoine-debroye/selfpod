# SelfPod 1.9.1 — full audit, 9 October 2026

Scope: statistics correctness, security, performance, UI/UX, dependencies.
Method: four independent code audits (one per area), plus live testing of the
dev server over a real socket (curl with Range/HEAD/conditional requests,
sqlite3 on the resulting database) and in a real browser at desktop and phone
widths. Every finding below was verified in code or reproduced live; items the
agents reported that did not hold up were dropped. `npm test`: 1304 pass, 0 fail.

Severity key: **H** fix soon · **M** worth fixing · **L** tidy-up / optional.

---

## 1. Statistics — are the numbers correct?

The pipeline is well built (one row per response, own visits excluded on every
preview path, aggregates agree with each other, indexes cover every query plan,
365-day retention runs daily). But four things make the headline numbers wrong
in ordinary use. All reproduced against the dev server.

| # | Sev | Finding | Evidence |
|---|-----|---------|----------|
| S1 | **H** | A `HEAD` request is counted as a completed **download** with the file's full size as bytes sent. Two HEADs on a 29 MB file made "Audio served" read 56 MB when ~30 MB left the server. Overcast, Apple's crawler and feed validators HEAD enclosures routinely. | Fastify exposes HEAD on every GET; `kind` is decided only by the `Range` header (`src/routes/public.js:619`) and `bytesSent` falls back to `Content-Length` (`public.js:70-72`). Nothing checks `request.method`. |
| S2 | **H** | A `304 Not Modified` on an episode is counted as a download. | Media route leaves `@fastify/send` validators on; every aggregate uses `status_code < 400` (`src/services/stats.js:247,272,302,348,418,441,508`). |
| S3 | **H** | A download the app **disconnected from mid-transfer** is logged as incomplete but still counted in Downloads, shown with a green 200 badge, and exported as `ok`. | `bytesSent` is `null` on abort (`public.js:70`), but `incomplete` requires `bytes_sent !== null` (`stats.js:637-642`); the existing test fakes `bytes_sent: 1000` so never exercises the real path. |
| S4 | **M** | Apple Podcasts always asks with `Range: bytes=0-`, so a complete Apple download is counted as a **stream**, never a download. Downloads are therefore undercounted per app, not uniformly. | `public.js:619`; the same route already classes `bytes=0-` as "from the start" at `:424`. IAB guidance treats `bytes=0-` as a download. |
| S5 | **M** | Day boundaries are an hour off on DST days in zones where the transition is within the UTC offset of midnight (Sydney, Auckland, Santiago…). Europe/London is unaffected. | `fromLocalInputValue` probes the zone offset at the wall-clock triple read as UTC (`src/lib/dates.js:128-131`). Tests only cover Europe/London and UTC. |
| S6 | **M** | Deleting an episode cascades away its whole request history, so show and instance totals shrink retroactively. | `media_access.episode_id … ON DELETE CASCADE` (migration 004). The `LEFT JOIN episodes` in `list()` suggests rows were meant to outlive the episode. |
| S7 | **M** | `AppleCoreMedia` is attributed to "Apple Podcasts", but it is the user agent of *any* iOS app streaming through AVFoundation (Overcast, Castro…). The "Which apps" chart over-credits Apple. | `stats.js:56-57`. |
| S8 | **L** | "vs the previous period" on the Audio served tile prints raw bytes (`+58,963,151`) instead of a size. | Stats page tile. |
| S9 | **L** | The comparison window is lopsided: current = N−1 full days + today's partial day, previous = N full days, so the delta is biased downward early in the day. | `src/lib/time-range.js:60-64`. |
| S10 | **L** | `/stats?showId=` filters only the access log; cards, chart and per-show table stay instance-wide. The failures card counts download/stream kinds only while "Failures only" counts every kind. | `src/web/routes/pages.js:741-772`, `stats.js:126,420`. |
| S11 | **L** | CSV is silently capped at 50 000 rows, newest first, while the page says it holds every row. | `pages.js:532`, `stats.js:96,619`. |
| S12 | **L** | A resume-after-re-cut request has its `Range` deleted before the kind/range are recorded, so the one case where the range explains a retry is logged as a plain download. | `public.js:583` runs before `:619`. |

What is correct and should not be touched: own-visit exclusion (session cookie
on every path, including the editor player, cuts previews and the reachability
check); half-open day boundaries in the configured zone; instance = Σ shows =
Σ episodes; CSV uses the same query as the page; failures (≥ 400) excluded from
downloads/streams; missing-file 404s and post-stat 500s both recorded with a
plain-language reason; no integer division or NULL mistakes in the SQL.

## 2. Security

Threat model: the media folder is an SMB share others can write to; the NAS can
see the LAN; one admin account behind a tunnel. Accepted risks (plain HTTP on
the LAN, unrestricted egress) are not listed.

| # | Sev | Finding | Evidence / exploit |
|---|-----|---------|--------------------|
| X1 | **M** | A decompression-bomb image on the share can OOM the container on every scan. No `sharp()` call sets `limitInputPixels`; the 40 Mpx constant exists but is never applied. A 16383×16383 solid WebP (a few hundred KB) dropped as `episode.webp`, or embedded in an MP3 tag under the 12 MB cap, decodes to ~1 GB on scan → OOM → restart → rescan → loop, with no banner. | `src/services/episode-art.js:58,77,82`, `src/services/covers.js:56,113,147,247`; `REMOTE_IMAGE_MAX_PIXELS` in `constants.js:356` unused. |
| X2 | **M** | The fingerprinter, transcriber and trimmer `readFile` the raw share path with no containment check and no size gate, while every *serving* route goes through `resolveContained()`. The scanner deliberately accepts symlinks. `ep.mp3 -> /dev/zero`, a FIFO, or a multi-GB file hangs or exhausts the heap on every scheduled pass once advert detection is on. | `src/services/ad-detect.js:114,147`, `transcriber.js:359-362`, `trimmer.js:185-188`; `scanner.js:354`. |
| X3 | **L** | Anonymous callers read full health-banner text via `/api/status` and the login page: show and episode titles, followed-feed hosts, data paths, UID/GID. Only the permission banners need to be visible before sign-in. | `src/routes/api/status.js:10-30`, `pages.js:89,109`. |
| X4 | **L** | Anyone holding the public URL can keep the admin locked out indefinitely: one wrong password every ~5 minutes resets the 300 s account-level backoff. (Per-source limiting is deliberately absent because of the tunnel; `MAX_ATTEMPTS_PER_WINDOW` is exported and unused.) Refusals return 401 rather than 429. | `src/plugins/auth.js:34,61-70,86-93`. Verified live: after 3 failures every attempt is refused until the window passes. |
| X5 | **L** | Changing the password in the UI does not invalidate other sessions (up to 30 days). The reset script does it right. | `auth.js:113-120` vs `scripts/reset-password.js:54`. |
| X6 | **L** | Supply chain: GitHub Actions by tag, base images without digests, whisper.cpp pinned by movable tag, `test` job has no `permissions:` block. | `.github/workflows/docker.yml`, `Dockerfile:10,45,52,82`. |
| X7 | **L** | Dependencies: `npm audit --omit=dev` reports 8 advisories. `sharp` ≤0.35.3 (libheif/librsvg, high), `music-metadata` 11.14 (crafted MP4/EBML/DSF crash the process — relevant because the scanner parses attacker-supplied tags), `js-yaml` via xmlbuilder2 (not reachable: no YAML is parsed), `ip-address` via @fastify/rate-limit (not used by the feed fetcher). | `npm audit` |
| X8 | info | `trustProxy: true` trusts every hop and compose publishes 8080 on all interfaces. Nothing security-relevant keys off forwarded headers today, so no exploit. | `src/app.js:33`, `docker-compose.yml:65`. |
| X9 | info | Session not regenerated on login. Verified not exploitable (`saveUninitialized: false`, no pre-login sid), but a one-liner for defence in depth. | `routes/api/auth.js:18`, `pages.js:115`. |

Checked and sound: cookie flags, bcrypt 12 with constant-time dummy compare,
CSRF via `Sec-Fetch-Site` with Origin fallback on every mutating route and no
state-changing GET, `requireAdminApi` on every API route and one scoped
`requireAdminPage` hook on fragments, `resolveContained` on all four serving
routes, the guarded fetcher (scheme/credential/port rules, every DNS answer
classified, pinned lookup so no rebinding, per-hop redirect re-validation,
size/stall/throughput timers, closed error enum, host-only logging), the
reachability check (admin + CSRF + rate-limited, fixed target, HMAC-proved
body), XML escaping and `]]>` neutralisation, allow-listed dynamic SQL,
`execFile` with argument arrays only, CSP `script-src 'self'` enforced by a
test, no stack traces on 5xx, token redaction in logs, Docker drops to PUID
with `cap_drop: ALL` and `no-new-privileges`.

## 3. Performance

Measured by a benchmark importing the repo's own modules against a synthetic
1-hour MP3 on an M-series Mac (a NAS Celeron is 3–6× slower).

| # | Sev | Finding | Evidence |
|---|-----|---------|----------|
| P1 | **H** | **Audio decoding and fingerprinting run on the HTTP thread.** 1 h of MP3 = 12.4 s of a fully blocked event loop (a 10 ms timer fired 2.1 s late). During that, every in-flight range request stalls, SSE heartbeats stop and `/health` does not answer; the Docker healthcheck times out at 4 s with 3 retries, so one long episode on a slow box can get the container restarted mid-pass. A fresh install fingerprints the whole library this way straight after the first scan. Only the two corpus *searches* were moved to the worker. | `src/lib/decode-audio.js:93-148` (no await), called from `ad-detect.js:182` and `transcriber.js:288`; `src/workers/audio-search.js` has only `repeatedAudio`/`headAnchors`. |
| P2 | **H** | The advert pass is not incremental and runs every rescan tick (5 min). `detectAnchors` loads **every** fingerprint into memory (~1.2 MB per hour of audio; 300 h ≈ 360 MB) and re-runs `locateAnchor` for every episode; `hearShow` parses every transcript and re-runs `locatePhrase` for every known read × every episode (1.7 s for 50×100). `episode_fingerprints.searched_at` and `ad_anchor_hits.checked_at` were added for exactly this and are written but never read. | `ad-detect.js:1596-1604,1678-1700,491-527,1319-1356`; `scheduler.js:132`; grep `searched_at` → only the upsert. |
| P3 | **M** | Whole-file buffering: trimmer holds ~2× file size (read + `Buffer.concat`); `sample.mp3` reads the **entire episode** off SMB and profiles it to serve a 10-second clip, on every play; the transcriber keeps the whole buffer alive across every whisper run. | `trimmer.js:188,201,208`; `routes/api/ad-segments.js:323-345`; `transcriber.js:362,395`. |
| P4 | **M** | No response compression for HTML/CSS/JS/JSON (only the feed is pre-compressed). First load ≈ 430 KB uncompressed; a 300-row episode table is hundreds of KB per render over the tunnel. | `src/app.js` registers no compress plugin. |
| P5 | **L** | Session `rolling: true` → one UPSERT per request including every `/assets/*` hit. | `src/plugins/session.js:84`. |
| P6 | **L** | SQLite hygiene: `PRAGMA optimize` never run; no `journal_size_limit`; hot statements re-prepared per call (`episodes.findByFilename`, `shows.isFolderRemoved`, `listSegments` N+1 inside `map`); four FK columns on the advert tables unindexed. | `src/db/index.js`, `episodes.js:98-110`, `shows.js:357`, `ad-detect.js:2139-2147`. |
| P7 | **L** | Boot: eager `sharp`/`xmlbuilder2`/`qrcode` imports (~0.8 s Mac), `chown -R node_modules` over 4 491 files every start, whisper probe loads the model at boot. In polling mode the watcher stats every file at ≤60 s *and* the scheduler rescans at the rescan interval — double the SMB stats on exactly the mount where it hurts. | `index.js:129,181,188`, `entrypoint.sh:81`, `watcher.js:102`. |
| P8 | **L** | Image ships both whisper models (250 MB) regardless of `WHISPER_MODEL`, plus `better-sqlite3/deps` (9.8 MB of SQLite source). | `Dockerfile:74-77`. |
| P9 | **L** | Dashboard: cover images are full 1400 px into a 250 px card (several MB per load over a tunnel); each show runs ~13 queries plus a segments N+1; "Rescan all" on N shows triggers N card fetches. | `show-card.eta:14`, `pages.js:230`. |

Already done well: feed cached per show with TTL + event invalidation, ETag
and Last-Modified that never go backwards, pre-compressed gzip/brotli, weak
ETag comparison for Cloudflare; media streamed with Range/206/416 from
`@fastify/send`, `private` cache-control; scanner fast path on (name, size,
mtime), 2 MB identity hash, metadata only on changed bytes; WAL + NORMAL +
busy_timeout; scans serialised and coalesced; SSE capped at 24 with cleanup;
immutable assets in production; remote feeds with conditional GETs and a byte
budget.

## 5. Recommended fix plan

Ordered by value for effort. Each tier is a self-contained PR.

**Tier 1 — correctness (≈ half a day)**
- S1–S3: in `trackAccess`, skip `HEAD`; record 304 with `bytesSent: 0` and exclude from downloads; treat an aborted download (`bytes_sent IS NULL` with error) as incomplete in every aggregate, the log badge and the CSV `result`. Add real-socket tests for HEAD, 304 and abort (the acceptance script can hold the HEAD/304 cases).
- S4: count `Range: bytes=0-` that delivers the whole file as a download.
- S7: attribute `AppleCoreMedia` as "iOS player" (or "Apple / iOS"), not Apple Podcasts.
- S8: format the bytes delta.
- U1, U2, U5, U11, U12: five small template/handler fixes.
- X7: `npm audit fix` and bump `sharp`, `music-metadata` (run the real-content checks after).

**Tier 2 — security hardening (≈ half a day)**
- X1: `limitInputPixels: REMOTE_IMAGE_MAX_PIXELS` on every `sharp()` that decodes share bytes; surface the failure as the existing artwork warning.
- X2: route pipeline reads through `resolveContained()`, `stat()` first, refuse non-regular files and anything over a cap, stream the hash.
- X3: allow-list the issue keys shown before sign-in.
- X5: delete other sessions on password change; X9: regenerate on login.
- X4: cap the lockout and add a per-source penalty (design choice — confirm first).

**Tier 3 — performance (1–2 days)**
- P1: move `fingerprintEpisode` and `decodeWindow` into the existing worker.
- P2: make the pass incremental using `searched_at`/`checked_at`; load fingerprints lazily; one `GROUP BY` for the held-episode count.
- P3: range-read `sample.mp3`; P4: `@fastify/compress` scoped to the web plugin; P6: `PRAGMA optimize`, hoist prepares, add the four FK indexes; P5: `rolling: false`.

**Tier 4 — UI/UX (1–2 days)**
- U3: `hx-indicator` + `hx-disabled-elt` on every decision/action form, a `htmx:sendError` handler, and move Check now / Teach to the enqueue-and-poll pattern `rescan` already uses.
- U4: skip SSE-triggered swaps while a form field inside the target has focus; move the forms out of the swapped region.
- U6, U7, U17: topbar wrap on narrow screens, card layout for the access log on phones, 44 px targets.
- U8: use `--accent-2` for button backgrounds and text-sized accent; `--ink-soft` for informational muted text.
- U9, U10, U14, U15, U16, U18, U19: individually small.
- U20: use a leading `YYYY-MM-DD` in the filename as the publish date when present (confirm: this changes existing feeds' order only for undated files, which stay on mtime).

**Tier 5 — later**
- S5, S6, S9–S12; X6, X8; P7–P9; U13 (extend the ad-blocker test to URL paths and alias the routes under `/cuts…`); U21–U23.

## 6. How each tier is verified
- `npm test` (new tests per fix), then `./test/acceptance/run.sh <image>` against a built container — HEAD/304/abort counting and the healthcheck-during-fingerprint case belong there, because `fastify.inject` fires `finish` twice and cannot time a blocked loop.
- UI fixes clicked in the browser at 1024 px and 375 px with an ad blocker enabled; confirm the *effect* (row changed, request happened), not the markup.
- Performance: re-run the scratchpad benchmark (`bench.mjs`, `block.mjs`) before and after P1/P2; the acceptance criterion is a 10 ms timer never firing more than 50 ms late while a 1 h episode is fingerprinted.
